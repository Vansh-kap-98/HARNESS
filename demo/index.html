Stage 02, the interesting half

What the compiler refuses

A decision model answers a fixed set of typed questions. Schema features that cannot be one typed question are refused and routed, never approximated — the refusal report is the schema layer's real output.

"type": "string"
free-form text with no enum or oneOf of consts → generative track
"minimum": 0, "maximum": 100
101 steps, over the 10-step score limit
"if" / "dependentSchemas"
changes which properties exist, so there is no fixed question set — the whole schema is refused, not one field
required & unsupported
no assembled instance could ever validate; the schema is out of scope rather than a bug to fix
The measurement

Where the decision model stops working

Accuracy against the number of options, on Banking77 intents. Option sets are nested — k=32 is exactly k=16 plus sixteen more — so a drop is attributable to the option count and nothing else.

The cliff is not the context filling up. The largest drop, −0.234 between 16 and 32 options, happens at 339 real tokens of a 512-token budget with nothing truncated. The step that does overflow, 32 → 64, costs less than half as much. Replicated across two distractor seeds: drops of 0.234 and 0.230.

Reading it

What this does and does not show

  • The decision model wins at every k, but the gap closes from 0.502 to 0.138, and that is entirely Laya falling rather than the baseline improving.
  • The limit is discrimination, not context. A larger context window would not move the cliff. Fine-tuning might, which makes 16 → 32 the thing worth attacking.
  • So it goes after a retriever, not instead of one. At a short option list it is excellent; it cannot be the layer that searches a large API catalogue.
  • The baseline was not handicapped. Options were ranked by summed log-probability, which favours short labels — it does over-pick them, about 3× chance by k=16 — but length-normalising recovers no accuracy, so the gap is real.
  • No latency claim belongs here. The baseline scorer evaluates every option exhaustively, so its wall-clock time is an artefact of the harness, not a property of the model.
  • Banking77 intents are a proxy for API operations. Real API descriptions are more confusable than banking intents, so the wall is likely lower, not higher.
  • Calibration is unreliable above ten options. The checkpoint ships an out-of-range temperature for its choice:11+ bucket and the library itself prints “treat confidence from the affected entries as uncalibrated”. Measured ECE at k=77 is 0.497.
